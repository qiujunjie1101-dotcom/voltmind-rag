## 实现范围

R1-4-2 在 `voltmind-server/` 实现文档解析结果的数据库基础，不包含 Python 解析器、切片算法、跨服务 HTTP、Embedding、Milvus、RAG 或前端改造。

Flyway V4 已在现有 MySQL 8.4.9 数据库从版本 3 迁移到版本 4，V1-V3 未修改。

## 代码结构

```text
com.voltmind.knowledge/
├── dto/DocumentChunkInput
├── entity/
│   ├── Document（增加版本和错误信息）
│   ├── DocumentStatus（增加 PARSED）
│   └── DocumentChunk
├── mapper/
│   ├── DocumentMapper（条件状态更新与行锁）
│   └── DocumentChunkMapper（有界批量写入与有序查询）
└── service/DocumentProcessingPersistenceService
```

数据库迁移位于 `voltmind-server/src/main/resources/db/migration/V4__add_document_processing_state_and_chunks.sql`。

## 版本与事务机制

- `startProcessing` 只允许 `PENDING / FAILED / PARSED` 通过单条条件更新进入 `INDEXING`，同时原子递增 `processing_version`。
- 保存结果前用 `SELECT ... FOR UPDATE` 锁定文档，检查文档仍存在、版本一致且状态仍为 `INDEXING`。
- 版本校验、旧 Chunk 删除、每批最多 200 条写入、`chunk_count` 更新和转为 `PARSED` 位于同一事务。
- 迟到版本返回 `STALE_PROCESSING_VERSION`，已删除文档返回 `DOCUMENT_NOT_FOUND`；外键同时阻止孤立 Chunk。
- 当前版本失败回写使用带文档 ID、版本和 `INDEXING` 状态的条件更新，不能覆盖新任务状态。
- Chunk 保存 SHA-256 内容摘要，复合唯一键为 `(document_id, processing_version, chunk_index)`。

## 数据库验证

容器 `voltmind-mysql` 使用 MySQL 8.4.9，状态健康。实际 `flyway_schema_history` 包含且仅包含一条成功的 V4 记录；`kb_document_chunk` 的主键、复合唯一键、文档外键、三个检查约束与索引均已通过 `information_schema` 查询确认。

迁移时业务库中没有文档记录；兼容性由集成测试验证：省略 `processing_version` 插入的既有格式文档得到默认值 0，并可合法进入 `PARSED`。

## 自动化验证

使用 JDK 17.0.20.1 执行 `mvn test`，42 项测试全部通过。新增覆盖包括 V4 与重复迁移、默认版本、`PARSED`、Chunk 写入和有序查询、重复索引拒绝、文档删除级联、旧版本和已删除文档拒绝，以及第二批写入失败时第一批 200 条一并回滚。

已知提示：当前 Flyway 版本正式验证到 MySQL 8.1，连接 MySQL 8.4.9 时会输出升级建议；迁移、校验和重复启动实际均成功。
