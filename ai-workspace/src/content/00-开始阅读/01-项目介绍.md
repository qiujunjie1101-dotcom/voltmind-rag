## Ai Workspace 是什么

**ai研发知识管理空间**

Ai Workspace 是一个可复制的项目级知识管理基础模板。它把需求、设计、技术方案、测试证据和协作记录组织为共享资料，让参与同一项目的人和 AI 使用一致的上下文。

当前工程维护模板本身。后续每个项目都可以基于它创建独立 workspace，保留通用目录、编辑能力和协作约定，再补充自己的项目介绍、资料和关联工程。详情见[项目愿景](../01-产品空间/01-产品设计/03-项目愿景.md)。

## 一个项目，一个空间

在 AI Coding 新范式下，交付所依赖的上下文会分散在需求文档、视觉稿、测试报告、代码仓库和协作记录中。Workspace 把这些资料组织到一个可阅读、可维护、可交接的空间。

| 资料 | 管理内容 |
| --- | --- |
| 产品设计 | 用户问题、需求范围、业务流程、验收标准 |
| 视觉与体验 | 视觉规范、交互稿、关键状态、设计交付 |
| 技术与前端设计 | 技术方案、接口约定、组件边界、实现记录 |
| 测试资料 | 测试计划、用例、缺陷、实际验证证据 |
| 运维资料 | 环境说明、发布步骤、监控和故障处置 |
| 项目管理 | 里程碑、依赖、风险和跨角色交接 |
| 空间配置 | 管理本机代码引用、角色与团队协作规则 |

## 空间和代码工程如何协作

一个 workspace 可以关联多个业务工程，例如前端、后端和基础服务。业务源码保存在各自工程，空间通过本地配置记录名称和路径。

- 团队共享资料、规则、角色技能和配置示例。
- 每个人维护自己的本地工程路径和角色，个人配置应只保留在本机；模板首次提交过的本地配置需要先取消 Git 跟踪，详见[初始化与配置说明](./02-Workspace-AI新范式介绍.md)。
- Workspace 自身的前端代码用于展示和编辑资料。
- 业务工程的开发、测试和 harness 在各自仓库维护。

网页中“连接本地项目”选择的是 **workspace 工程目录**，用于编辑这里的资料。关联业务仓库则配置在 `code/projects.local.json`，两者用途不同。

## 本地配置与协作规则

通过 `npm run dev` 启动空间后，可在“空间配置 → 配置中心”确认目标目录并授权绑定当前空间，读取和保存个人配置。不支持文件夹选择接口的浏览器也可使用这条保存路径。导入配置先成为页面草稿，绑定后仍需点击保存才写入本机文件。

资料和 Harness 编辑使用浏览器文件夹授权；静态部署的配置页面可使用文件夹授权或导入、下载配置。授权范围和实际保存结果会在页面提示。

根目录 `AGENTS.md`、角色技能、`harness/templates/` 和 `harness/tasks/` 共同保存协作规则、资料模板、任务进度和交接。角色目录是协作边界，业务工程自身的开发规则仍由对应工程维护。

## 当前状态

模板提供资料阅读、本地编辑、工程引用配置、角色技能和基础 harness。复制到新项目时，应排除个人配置和旧任务记录，再初始化自己的角色与工程路径，替换项目资料。已有搭建教程保留历史来源说明，不代表新项目的需求或验证结果。

当前范围见 [MVP 范围](../01-产品空间/01-产品设计/02-MVP%20范围.md)。后续优化依据真实项目使用反馈推进；尚未验证的使用假设与实际结果分别记录。
